# AI

Two features use the model: roadmap generation and plan chat. Both follow the same three rules.

1. **The model never supplies facts about fees, authorities or links.** Costs marked as official come from `feeReferences`. Links come from `sources`. Anything else is labelled an estimate.
2. **Nothing the model returns is stored before validation.** Roadmap output is parsed with Zod, sanitized, and written in one atomic update.
3. **Chat is read-only.** It can suggest a change; the user makes it.

## Provider and model

**Not chosen yet (A5 in [01-product.md](01-product.md)).** The owner decides after a short trial at the end of Week 1: a draft prompt and roadmap schema, a few sample ideas and hand-entered fees for two emirates, run on each candidate. The full quality check confirms the choice at the end of Sprint 2. Until then, everything that uses AI is built and tested in [sample mode](#sample-mode).

The rest of the app never talks to a provider directly. It calls two functions: `generateRoadmap()` in `src/lib/roadmap/generate.js` (templates in `src/lib/roadmap/templates.js`) returns a roadmap, and `answerQuestion()` in `src/lib/chat/answer.js` answers a chat question. Today both are the built-in sample assistant. The chosen provider plugs in behind them, so switching later changes those two files and the environment variables, nothing else. The Vercel AI SDK (`ai` package) is the likely way to build that module, because it already offers both functions across the major providers; it is confirmed together with the provider.

What the provider must support:

| Need | Why |
| --- | --- |
| Structured JSON output against a schema | The roadmap is saved only after it parses |
| Streaming | Chat answers appear as they are written, and generation reports progress |
| Long outputs, around 16,000 tokens in one answer | A full roadmap is about 11,000 output tokens |
| Strong instruction following | The grounding rules above only work if the model obeys "use only the supplied ids" |
| A monthly spend limit, or a free tier | Cost stays capped while the app is a demo |
| Data-use terms that exclude training on submitted content | Intakes contain people's business ideas; a tier that trains on them is ruled out |

Candidates to compare when the decision is made: Anthropic (Claude), OpenAI, and Google (Gemini). Run the [quality check](#quality-check) against each one and compare the reports with the cost estimate below.

| Setting | Roadmap generation | Chat |
| --- | --- | --- |
| Transport | Streamed, final result read at the end | Streamed to the browser |
| Output limit | About 16,000 tokens | About 8,000 tokens |
| Output format | Structured output with a JSON schema generated from the Zod roadmap schema | Markdown text |
| Prompt caching, where the provider offers it | System prompt and reference-data block | System prompt |

**Refusals and truncation.** Check why the model stopped before reading the result. A refusal or an answer cut off at the output limit marks the generation as failed with a plain message.

## Roadmap generation

### Input

The intake form: idea, emirate, sector, jurisdiction preference (mainland, free zone, unsure), budget in AED, target customers, team size.

### Context sent to the model

The server loads, for the plan's emirate plus federal rows (`emirate is null`):

- all active `feeReferences`, both jurisdictions, so the model can compare them;
- all active `sources`, capped at 60.

Each row gets a short id (`F1`, `F2`, … and `S1`, `S2`, …) that maps back to its `ObjectId` on the server. Short ids cost fewer tokens and are harder for the model to garble. The block is serialized in a stable order so a provider's prompt cache can reuse it across users in the same emirate.

### System prompt outline

- You plan business setup in the UAE for students and first-time founders. Write plainly.
- Use a fee reference's range for any cost you mark `reference`, and list its id. For any other cost, give your best range and mark it `estimate`.
- Cite sources only by the ids supplied. Never write a URL, a fee, or an authority name that is not in the supplied data. If an authority is not listed, describe its type ("the emirate's economic department").
- Recommend mainland or free zone and say why, taking the stated preference and budget into account.
- If the budget looks too small for the plan, say so in the risks.

### Output schema

```ts
Roadmap = {
  summary: string
  recommended_jurisdiction: "mainland" | "free_zone"
  jurisdiction_reason: string
  phases: Array<{
    title: string
    description: string
    tasks: Array<{
      title: string
      description: string
      authority: string
      cost_min_aed: number
      cost_max_aed: number
      cost_basis: "reference" | "estimate"
      fee_ref_ids: string[]   // F-ids
      source_ids: string[]    // S-ids
      est_days: number
    }>
  }>
  budget_items: Array<{
    category: BudgetCategory
    label: string
    estimated_aed: number
    recurrence: "one_time" | "monthly" | "yearly"
    cost_basis: "reference" | "estimate"
    fee_ref_ids: string[]
  }>
  documents: Array<{ name: string; description: string; required: boolean; source_id: string | null }>
  risks: Array<{
    title: string
    description: string
    likelihood: "low" | "medium" | "high"
    impact: "low" | "medium" | "high"
    mitigation: string
  }>
}
```

Counts and lengths (3–7 phases, 2–8 tasks per phase, 3–8 risks, summary under 600 characters) are checked by Zod after parsing rather than relied on in the JSON schema. Providers' structured-output modes support only a subset of JSON Schema keywords.

### Sanitizing, in order

1. Map short ids to `ObjectId`s. Drop any id that was not supplied.
2. A cost marked `reference` with no surviving fee id becomes `estimate`. Fee ids are not stored themselves: each surviving fee reference adds its `sourceId` to the task's `sourceIds`, so the user can see where the number came from.
3. Negative amounts fail validation. If min > max, swap them.
4. A `reference` cost must lie within the cited fees' combined range: the sum of their minimums to the sum of their maximums. Amounts outside it are set to that range, so a cost labelled official always matches the fee rows behind it.
5. Clamp `est_days` to 1–365. Trim all strings.
6. Keep array order as display order; the plan document stores arrays in that order.

If Zod still rejects the result, retry once, then mark the plan `failed`.

### Saving and progress

The whole roadmap (phases, tasks, budget items, documents, risks) is written into the plan document with one `updateOne`, which also sets `status` to `ready`. The filter matches on `_id`, `ownerId` and `status: "generating"`, so the save is atomic without a transaction, and a plan that was deleted or regenerated meanwhile is left alone.

The route streams coarse progress events to the browser (started, writing, saving, done). The plan's `status` field is the source of truth: a page refresh during generation shows the generating state and polls. Generation does not abort when the browser disconnects; it finishes and saves. A plan still `generating` after five minutes, the function limit, is shown as failed, with a retry button.

**Regenerate** creates a new plan from the same intake. The old plan and its edits stay. Nothing is overwritten.

## Chat

`POST /api/plans/[id]/chat` with `{ message }`, streamed back.

1. Check that the caller owns the plan and is active, then call `consumeQuota(userId, "chatMessages")` from `src/lib/quota.js` (the atomic `aiUsage` update described in [03-schema.md](03-schema.md)).
2. Store the user's message.
3. Build the request, most stable first so a prompt cache can reuse the prefix:
   - system prompt;
   - plan snapshot: summary, phases and tasks with status, budget items and totals, documents with obtained flags, risks;
   - up to 8 sources for the plan's emirate plus federal, ranked by the MongoDB text index against the question (see [Source search](02-architecture.md#source-search)), each with its URL;
   - the last 20 messages;
   - the new message.
4. Stream the answer. When it completes, store it with token counts. If the stream fails, store nothing for the assistant and show a retry button.

The chat system prompt tells the model to answer from the snapshot and sources, cite sources as links using only the supplied URLs, say when something is not covered and point to the authority, and describe changes for the user to make rather than claiming to make them.

**Prompt injection.** The plan text comes from the plan owner and only reaches that owner's chat. Sources are admin-curated. Mentor posts and other users' content never enter a model request.

## Quotas and cost

Default daily limits per user, in `src/lib/quota.js`: 5 generations and 40 chat messages. Every call is counted in `aiUsage`, and the admin console shows totals. Token counts are planned for when a provider is connected.

Cost depends on the provider and model, so this section estimates tokens, not dollars. Multiply by the chosen model's price per million tokens. The figures are guesses until Phase 1 measures real counts.

| Call | Input tokens | Output tokens |
| --- | --- | --- |
| One roadmap | ~10,000 | ~11,000 |
| One chat message | ~8,000 (partly cacheable) | ~1,500 |

At 200 active users making 2 plans and 20 chat messages each per month, that is about 4 million input and 4.4 million output tokens for generation, and 32 million input and 6 million output tokens for chat. Chat dominates. Levers, cheapest first: better cache hits, a shorter chat history, then a cheaper model for chat only. Using two models is the owner's decision, made after measuring quality on the eval below.

## Sample mode

Until a provider is connected, the app runs in sample mode: `src/lib/roadmap/generate.js` builds roadmaps from templates and the official fee references, and `src/lib/chat/answer.js` answers from the plan and the matching sources. Every answer says it comes from the sample assistant. Local development and all the tests use it, so no API key is needed. A switch between sample and live answers, and recorded real outputs for the tests, are planned for when the provider is chosen.

## Quality check

A quality-check script (planned, not written yet, because no provider is connected) will run ten fixed intakes against the live model and write a Markdown report. The intakes cover all seven emirates, both jurisdictions, budgets from AED 5,000 to AED 500,000, and sectors such as a food truck, online store, consultancy, mobile app, salon, tutoring and trading. The script will then ask ten fixed chat questions about one of the generated plans, including two that the plan and sources cannot answer, and add the answers to the report.

Review each output against this checklist before merging any prompt or schema change, and use the same checklist to compare candidate providers:

1. It validates, and the sanitizer changed nothing beyond dropping unknown ids and clamping `reference` costs.
2. Every `reference` cost cites the fee references that really cover that task, not just any fee from the same emirate.
3. No fee, authority or URL appears that was not in the supplied data.
4. Tasks come in a workable order, with dependencies before the steps that need them.
5. Budget items are plausible against the stated budget, and an under-funded plan says so in its risks.
6. A first-time founder could follow it without looking up jargon.
7. Each chat answer links only to supplied sources, and the two unanswerable questions get "not covered" with a pointer to the right authority.
